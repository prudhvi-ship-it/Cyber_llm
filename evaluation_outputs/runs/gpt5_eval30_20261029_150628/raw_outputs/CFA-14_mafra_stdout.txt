Defensive Recommendation:
- Restrict network access to etcd client port 2379 and peer port 2380 so only trusted components can connect (e.g., firewall rules, security groups, Kubernetes NetworkPolicies).
- Enforce mutual TLS (mTLS) for etcd client connections; require and validate client certificates with appropriate revocation checks.
- If relying on etcd Auth/RBAC, ensure it is enabled and properly scoped; periodically audit roles, permissions, and lease usage.
- Minimize or disable the HTTP v3 gateway if not required; prefer secured gRPC endpoints behind mTLS and internal network boundaries.
- Upgrade etcd to a currently supported, patched release per vendor guidance and security advisories; schedule regular updates.
- Monitor and alert on unexpected /v3/lease/*, /v3/watch, and /v3/kv operations, especially from atypical client IPs or identities.
- Segment management-plane services (e.g., API gateways and etcd) onto isolated networks to reduce exposure.
- Enable and retain detailed etcd server logs; routinely review for anomalous access patterns or failed auth events.
